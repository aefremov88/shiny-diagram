# Documentation Standards

> **Kind:** Defining  
> **Document state:** Maintained  
> **Implementation state:** Aspirational  
> **Last reviewed:** 2026-08-18  
> **Scope:** Rules and structure for all documentation in this repository — centralized doc/ folder and decentralized planes  

## 1. Purpose

These Standards describe document management system in Shiny-diagram repository. It defines rules of documentation, structure of document storage and document maintenance procedures. They don't describe content within the documents

## 2. Document kinds

There are two kinds. The difference is the direction of truth.

- **Defining** — hand-written. States rules, standards, decisions, or facts. Is supposed to be source of truth - code and other documents must comply with it. When a defining document and the code disagree, one of them is wrong and the disagreement must be resolved. Examples: this document, `system/architecture.md`, product specifications.
- **Collecting** (a "plane", short for "management plane") — generated by a script from other files (code or other documents). In this case these files are source of truth and the plane is used to provide aggregate view of this truth. Never hand-edited; fixed by changing the source and regenerating. Examples: planes, `docs/index.md`. Planes are collected by scripts in `scripts/` and regenerated by `npm run planes`; the check pipeline fails when a plane is stale.

## 3. Where documentation lives

Defining documents live under `docs/`:

- `docs/` root — the generated index and this standards document.
- `docs/system/` — documentation of code: architecture, coding standards.
  - `docs/system/layers/` — documentation that describes one architecture layer.
  - `docs/system/tooling/` — architecture of modules beyond the core layers, e.g. the debugging utils
- `docs/workflows/` — how work is done, actor-agnostic (both agents and human programmers)
- `docs/agents/` — agent manifests: general information (context, communication rules, etc) and role-specific agent manifests
- `docs/product/` — documentation of product features and behaviors

Collecting documents live with their sources, not under `docs/`:

- A plane lives in the root of the code area it collects. Example: `webview/src/Ui/GESTURE-TARGETS.md` collects gesture facts from the UI library. Reason: the plane changes together with that code.
- `docs/index.md` is the one collecting document inside `docs/`, because its sources are the documents themselves.

The index lists both: all documents under `docs/` and all planes.

## 4. Metadata header

Every document — defining and collecting — starts with this header, directly after the title:

```markdown
> **Kind:** Defining | Collecting  
> **Document state:** Maintained | Work-in-progress | Stale  
> **Implementation state:** Aspirational | Implemented  
> **Last reviewed:** YYYY-MM-DD  
> **Scope:** one sentence: what this document covers  
> **Generated by:** link to the generated script (for planes only)
```

Some combinations:

- `Maintained | Implemented` — the document is kept true, and the implementation complies with it.
- `Maintained | Aspirational` — the document is kept true as the target state, but the implementation does not yet fully comply with it. The gap must be known and controlled.

Rules:

- Each line ends with two trailing spaces, so lines render separately.
- **Kind** — identifies the document as `Defining` or `Collecting`, as defined in chapter 2. 
- **Document state** — describes the reliability of the document. `Maintained` means it is kept true and is safe to rely on. `Work-in-progress` means it is incomplete and may change. `Stale` means it is not source of truth because it lags behind.
- **Implementation state** — describes the relationship between a defining document and the implementation. `Aspirational` means the document defines a target state that is not yet fully implemented. `Implemented` means the implementation complies with the document.
- **Last reviewed** — records the date of the last update by human or agent. For a collecting document, the generator writes the generation date.
- **Scope** — describes in one sentence exactly what the document covers. The index uses this sentence as the document's description.

Additionally, planes have a standard warning right below metadata header:

```markdown
<!-- Auto-generated Never edit by hand. Regenerate with: npm run planes -- document-index -->
```



Plane generators emit this header themselves. The index generator fails with an error on any document with a missing or malformed header; a failing index build is the mechanism that keeps this standard enforced.

## 5. Index generation

`docs/index.md` is generated; it is never edited by hand.

- The generator scans `docs/**/*.md` and all registered planes, reads each header, and renders one table: path, kind, state, scope.
- The generator is part of the planes pipeline (`npm run planes`); the check pipeline fails when the index is stale, same as for any plane.
- A new document becomes part of the repository by having a valid header; the index picks it up on the next generation. There is no separate registration step for `docs/` documents. Planes are registered in the planes pipeline, which is their existing discipline.

## 6. Writing standards

Documentation follows two principles.

**Principle 1 — reduce the reader's cognitive load.** Rules:

- **Simple language.** Plain common words. No idioms, no metaphors, no coined labels. Short sentences over long ones. Domain terms are allowed only when the document defines them before first use.
- **Top-down communication.** Core idea or insight first; supporting evidence and clarifications after.
- **Structured enumeration.** If a paragraph enumerates more than two logically parallel objects, present them as bullet points. The best number of bullet points is 3–7.
- **Logical parallelism.** Chapters and bullet points must describe logically parallel objects, ideally with the same internal structure.
- **No repetition within a document.** Do not restate what the document already said; repetition forces the reader to reconcile the copies.


**Principle 2 — cover the domain fully, each fact exactly once.** Rules:

- **One home per fact.** Every fact belongs to exactly one document; other documents link to it. If a fact fits two documents, the split between those documents is wrong — fix the split.
- **No gaps.** Every rule a developer or agent needs is written somewhere. A question that the documentation cannot answer is a coverage bug: fix it by adding the fact to its home document.

**Conventions:**

- Headings: sentence case (`## Document kinds`, not `## Document Kinds`).
- File names: kebab-case, `.md`.
